# 我的博客安全审计并修复

这次审计覆盖博客前台、管理端 API、登录与令牌、评论、文件上传、访问日志、反向代理请求头和生产配置。目标是确认公开接口不会越过权限边界，异常请求不会轻易绕过安全规则，错误响应不会把服务内部细节返回给访客。

## 审计结论

没有发现未登录用户可以直接读取用户、访问日志、IP 风险规则或后台内容的路径。管理接口继续要求 JWT 和对应角色权限，公开博客接口只返回已发布内容，上传文件继续执行扩展名、MIME、文件头和大小校验。

本轮确认并修复了以下问题：

### 1. API 根目录泄露路由清单

原来的 `/api/` 会返回 DRF 路由索引，公开列出用户、访问日志和安全规则等接口名称，浏览器还可以看到可浏览 API 页面。这不会直接返回数据，但会降低攻击者的枚举成本。

现在精确的 `/api/` 返回 404，具体子接口保持不变。例如未登录访问 `/api/users/` 仍然返回 401，公开文章接口仍然正常工作；同时 API 默认只返回 JSON，不再暴露可浏览 HTML 接口。

### 2. 来源 IP 可以被伪造

应用原先无条件信任 `X-Forwarded-For` 的第一个值。攻击者可以自行构造这个请求头，伪造访问日志中的来源 IP，绕过 IP 黑名单、限流规则或影响风险画像。

现在只有来自配置好的可信代理（线上 Nginx 默认是本机回环地址）时才读取转发头；直接连接应用的请求始终使用对端地址。测试覆盖了可信代理和不可信对端两种情况。

### 3. 登录接口缺少默认失败限流

登录失败不会绕过密码校验，但没有默认的失败频率上限，容易被用于密码猜测和日志噪声攻击。

现在同一来源 IP 的登录请求限制为每分钟 10 次，超过后返回 429，并保留正常登录和令牌轮换流程。

### 4. 匿名评论没有默认限流

公开评论接口有内容审核和长度限制，但此前可以持续提交大量评论，容易造成垃圾内容和数据库写入压力。

现在匿名评论创建限制为每分钟 10 次。公开阅读和评论审核接口不受这条写入限流规则影响。

### 5. 调试配置默认值不安全

`DJANGO_DEBUG` 缺失时原来默认开启调试模式。线上环境一旦漏配环境变量，异常响应可能包含堆栈和内部路径。

现在调试模式默认关闭；只有明确设置 `DJANGO_DEBUG=True` 才进入开发模式。生产环境同时要求提供 `DJANGO_SECRET_KEY`，测试运行使用隔离的临时密钥。

## 已验证的防护

- 刷新令牌使用 HttpOnly、Secure、SameSite Cookie，响应体不返回长期 refresh token。
- 用户注册、用户管理、文章管理、分类、标签、文件管理和访问日志接口按角色控制权限。
- 公开接口只返回已发布文章和已审核评论，评论公开序列化器不会返回邮箱。
- 上传内容检查文件头，公开文件响应设置 `X-Content-Type-Options: nosniff`；非安全内联类型按附件下载。
- API 异常在生产模式下使用稳定错误消息，调试信息不在默认生产配置中返回。
- HTTPS、HSTS、Secure Cookie、X-Frame-Options、CSP 和 Referrer-Policy 已在生产响应中生效。

## 验证结果

后端完整测试共 132 项，132 项通过，其中 1 项按既有测试标记跳过。新增测试覆盖 API 根入口、子路由、代理 IP 伪造、登录失败限流和匿名评论限流。

使用生产参数执行 `manage.py check --deploy` 时没有发现阻断性错误，只提示 HSTS preload 尚未开启；这项设置需要确认所有子域都永久使用 HTTPS 后再启用。

线上发布后再次验证：`/api/` 返回 404，`/api/users/` 未登录返回 401，Gunicorn 和 Nginx 服务均为 active。

## 后续建议

安全修复降低了当前暴露面，但不能替代持续维护。后续应继续保持依赖升级、备份恢复演练、登录和评论限流告警，并定期检查 Nginx 的代理头配置和环境文件权限。SSH 远程维护策略仍应结合云防火墙、密钥登录和堡垒机逐步收紧。
